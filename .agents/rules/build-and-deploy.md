# Building and deploying this application

Read this before changing the build, packing a deployment archive, building or editing the Docker image, setting `CDN_BASE_URL`, or building for another platform. The deployment process itself is in the [deployment Skill](../skills/nocobase-deployment/SKILL.md), and dependency placement and the build failure table are in [where to declare a dependency](../skills/nocobase-app-development/references/dependencies.md).

## Client typechecking

Keep `types: ["node"]` in the client `tsconfig.json`. Shared contracts from database and lifecycle packages resolve to their TypeScript sources in a workspace and require Node.js declarations during typechecking. Declare that requirement explicitly instead of relying on unrelated plugin imports to load the declarations; type-only imports still disappear from the browser bundle.

## CDN assets at build time

`CDN_BASE_URL` sets Vite's `base` only during a production build: `CDN_BASE_URL=https://cdn.example.com/my-app/v1/ pnpm build`. Use a full HTTPS URL ending in `/`; unset, empty or whitespace-only values keep the default `./`. `pnpm build` reads it from the process environment, then `.env.local`, then `.env`; development ignores it and continues using `APP_BASE_PATH`. It is a build parameter, absent from `config variables` and `dist/variables.json`, with no `config.yml` setting. Changing it requires rebuilding.

Upload the static files from `dist/client/` to that CDN prefix with their directory structure preserved, and enable CORS for the application's origin. Keep `index.html` and the complete client tree on the application server so it can inject runtime configuration into HTML and serve files still addressed there. Use `resolveAssetUrl('/assets/logo.png')` from `@nocobase/app-client` for a file shipped as `dist/client/assets/logo.png`; template logos use this helper. It reads Vite's build-time `BASE_URL`, uses an absolute HTTP(S) CDN base when configured, and otherwise falls back to the runtime mount path. Keep API paths, page links and runtime-generated files on `resolveAppUrl`. Vite does not rewrite arbitrary URL strings. The guide's Deployment section (`docs/guide.md`) describes deployment and Docker usage.

For a Docker source build, pass `--build-arg CDN_BASE_URL=https://cdn.example.com/my-app/v1/`. With `DIST=prebuilt`, set `CDN_BASE_URL` when building `dist/` beforehand. Neither a prebuilt image's build argument nor `docker run -e CDN_BASE_URL=...` can change compiled asset URLs.

## Packing the build for a deployment

`pnpm build --tar` writes `storage/exports/dist.tar.gz` after the build. The archive holds `dist/` as a directory next to `config.example.yml`, with the `Dockerfile` and `Dockerfile.dockerignore`, so extracting it produces exactly those paths rather than scattering `server/` and `node_modules/` into whatever directory you unpacked in, and a server can build the image from it alone with `docker build --build-arg DIST=prebuilt .`.

`config.example.yml` travels with it because a deployment has to write a `config.yml` before it can start — `pnpm nocobase config init`, run inside `dist/`, does that from the example, in place, and `pnpm nocobase config check` there verifies it, database connection included, before the first start — and the example is the only statement of what may go in it. Directories of executable shims are left out: a `.bin` entry points at a path on the machine that installed it, and a dangling one makes `pnpm install` in the extracted tree report a corrupt store rather than repair it.

Without `--tar` no archive is produced, which is what you want when the build is only going to be run locally.

## Building a Docker image

`Dockerfile` and `Dockerfile.dockerignore` build this application from its sources: a build stage runs `pnpm install --frozen-lockfile` and `pnpm build`, and a `node:24-bookworm-slim` runtime stage receives `dist/` and `config.example.yml` only. The runtime has no pnpm, so it runs the two `dist/package.json` scripts directly: `start` is `node ./server/standalone.js`, which the image starts as `node dist/server/standalone.js`, and `nocobase` is `node ./cli/index.js`, run as `node dist/cli/index.js <topic> <command>`. The deployment root is `/app`, so configuration is `/app/config.yml` and storage is `/app/storage`, both mounted at runtime.

The client is not tied to a mount path, so `APP_BASE_PATH` is a runtime variable, `/main` in the image unless the container is started with `-e APP_BASE_PATH=<path>`; the health check probes the same path. The build stage runs on `$BUILDPLATFORM` and passes `--target linux-$TARGETARCH`, so a multi-platform build does not compile under emulation; do not move the build stage to the target platform or switch the runtime to Alpine, which would need the musl target. Keep `Dockerfile.dockerignore` beside the Dockerfile: BuildKit reads it only there, and without it `config.yml`, `.env`, and `storage/` enter the build context.

`--build-arg DIST=prebuilt` skips the build stage and packages the `dist/` in the context instead, selected through `FROM dist-${DIST}` so BuildKit never runs the stage it does not use. That stage refuses a `dist/` whose `nocobase.buildTarget` is not linux, glibc, the target architecture and the image's Node major, and one from an `@nocobase/app-cli` that does not record `nocobase.relocatable`, whose client is tied to the path it was built for. The ignore file re-includes `dist/` last and whole, so dependency directories inside it named like excluded paths (`langchain/storage`) survive, and then excludes `dist/.env`, which can carry `DB_PASSWORD` from local `.env` files. Keep those rules in that order.

## Building for another platform

`pnpm build --help` (or `-h`) lists build options and exits without loading build dependencies, running hooks, or modifying `dist/`. Every successful build records `nocobase.buildTarget` in `dist/package.json`, including builds with no native modules: `platform`, `arch`, `libc`, `nodeMajor`, and `nodeAbi`. Use `libc` only for Linux; its value on other platforms is a compatibility placeholder. Deployment checks should compare these fields with the host runtime and also respect `engines.node`. With `--target current` (the default), the Node version and ABI come from the running process; an explicit platform target defaults to Node 24 unless `--node-version` is supplied.

`pnpm build` targets the machine it runs on, so `pnpm build && pnpm start` works. A deployment build says where it is going: `--target linux-x64`, `--target linux-arm64`, `--target linux-x64-musl`, plus `--node-version` when the server's Node major differs. Every build prints the platform it produced and records it in `dist/package.json` under `nocobase.buildTarget`.

A `.node` binary must match the target platform, architecture, and C library; addons using the Node ABI must also match its version. `better-sqlite3` 13 uses N-API and bundles its platform binaries, so cross-platform builds retain the target's binary, including the separate `linuxmusl` build for Alpine. `pg`, `mysql2`, and `tedious` are plain JavaScript, so an application using only those is portable as built.

## Compiled migration and seed manifests

The application build generates `.manifest.json` in each compiled migrations and seeds directory after server compilation, path rewriting, and `afterServerBuild` hooks. Keep the manifest generator in the build when customizing it. Plugins generate their own manifests when built; an application must not regenerate manifests for installed dependencies.

TypeScript and compiled JavaScript use the same source checksum for migration history, while the loader separately verifies emitted JavaScript. Marked JavaScript requires its manifest. For a database with old raw JavaScript checksums, first run the compiled representation with matching original output; verified legacy hashes are converted under the task lock. Unreproducible old output remains an error. Never edit historical migrations, and never edit the history table by hand, to resolve an upgrade failure; `pnpm nocobase db repair` is the supported way to realign a checksum you can account for, and `pnpm nocobase db redo` the way to re-run a migration whose branch is still unmerged.

## Server start log

`pnpm dev` owns the ready banner and public URL; `APP_SERVER_START_LOG=false` suppresses the underlying listener announcement through the `env` of `server/config/server.ts`. Keep that mapping when editing deployment environment settings. Request starts, request headers and config diagnostics use DEBUG; the normal INFO output contains completion summaries. See the shared application development Skill for hosted logging and upgrade limits.

## In this application

The application's one build step is the `afterServerBuild` hook in `cli/itam.ts` (registered in `cli/plugins.ts`). It runs `scripts/copy-seed-assets.mjs`, which copies the seeds' data files (`database/main/seeds/assets/`) next to the compiled seeds and the assistant's skills (`ai/skills/`) to `dist/ai/skills/`, where the server reads them at its first start. A deployment's `config.yml` needs `secrets.keys`, or the assistant's model services cannot be stored; the guide's Configuration section (`docs/guide.md`) shows it.

## Redis jobs and queues

Since `@nocobase/jobs` 1 and `@nocobase/queue` 1 (2026-10-30, with Demo Mode 0.2.0-beta.6), their Redis backends live in the commercial `@nocobase/app-plugin-jobs-redis` and `@nocobase/app-plugin-queue-redis` Server plugins, which come from the customer registry rather than npm, and `server/config/jobs.ts` and `queue.ts` declare memory only. A deployment that names Redis in `jobs`, `queue`, `scheduler.jobs` or `mail.jobs` installs and registers that plugin on every producer and consumer and spells out `adapter: redis`; `connection` alone no longer selects it, and an unregistered backend fails rather than falling back to memory. ITAM's work agents' queue (`itamAgentRuns`) moves the same way.

That upgrade moved the framework packages ahead of the template: `nocobase.defaultTemplateVersion` stays 1.0.0-beta.84 because only these configuration files, their test and `config.example.yml`'s jobs section were taken from 1.0.0-beta.85, so the next template upgrade finds them already merged and everything else still to do.

Demo Mode 0.2.0-beta.9 (2026-11-06) moved the cohort again, to `@nocobase/app-server` 5 and `@nocobase/caching` 1, without template files: the app never imported the removed `@nocobase/app-server/mailer` entry, its notification configuration already comes from `@nocobase/app-plugin-notification-providers/config`, and the `mailers` section app-server 5 adds is optional, so `server/config/mailers.ts` waits for the next template upgrade and password reset keeps the inline `auth.email` sender.

## Deploying to Studio

Run release checks under Node 24, matching CI (2026-10-26). Node 26's native `localStorage` conflicts with the jsdom test environment and causes browser-storage tests to fail; on a machine using mise, select the installed Node 24 with `mise exec node@24 -- pnpm test`.

Since `@nocobase/app-plugin-foundation` 0.1.0-beta.13 (2026-11-06, with Demo Mode 0.2.0-beta.9), every application start on a database without a Foundation snapshot queues a scan, and in a source checkout that scan parses the application's TypeScript synchronously (`source-evidence.js` / `static-values.js`), blocking the event loop for tens of seconds; a test application's `close()` waits for it. Tests that boot the application then fail with `Hook timed out in 30000ms` at `server.close()` while their assertions pass, worst on a loaded machine. Production reads the prebuilt `dist/server/foundation-modules.json` and is not affected. Until the plugin stops blocking on start, `tests/support/setup.ts` switches the automatic scan off for test applications (Foundation stays registered; set `ITAM_TEST_FOUNDATION_SCAN=1` to keep the scan for a test that needs it). Remove that block once a Foundation release no longer blocks, and recheck it when Foundation is upgraded, as it wraps the provider's `start()`.

A release is deployed to the application `itam` in three NocoBase Studios — internal (studio.v2.test.nocobase.com), cn (solutions-cn.nocobase.com) and global (solutions.nocobase.com) — by `.github/workflows/deploy-studio.yml`, as NocoCRM's is (2026-10-23). A release is a commit `Release <version>` on `main` that sets `version` in `package.json`, pushed with the tag `v<version>` on it. Make one by running `.github/workflows/release.yml` (Actions → Release → Run workflow, on `main`; 2026-11-06, as NocoCRM's): `scripts/ci/release-version.mjs` sets the version — the current one with its last number increased by one, unless a later version is named — then the workflow runs `pnpm lint`, `pnpm format:check`, `pnpm typecheck` and `pnpm test` on that change, commits, tags and pushes commit and tag together as `github-actions[bot]`, and, while its `deploy` switch is on (the default), calls `deploy-studio.yml` with the tag. A failing check stops it before anything is pushed, and a push to `main` meanwhile makes its push fail. A tag pushed with the workflow's own token starts no workflow, which is why the release calls the deployment instead of relying on its tag; so `deploy-studio.yml` takes the release from `RELEASE_REF` and `RELEASE_SHA`, which it sets, never from `GITHUB_REF` or `GITHUB_SHA`, which are the caller's in a called run. `main` has no branch protection; if it gains some, allow `github-actions[bot]` to push. A release made by hand — the commit and tag pushed from a machine, after running `pnpm lint && pnpm format:check && pnpm typecheck && pnpm test` and going no further while one fails — still starts the deployment through its tag. The deployment runs the same checks again, unless the release workflow has just run them on that commit, builds once with `pnpm build --target linux-x64 --node-version 24 --tar`, then deploys the archive to each Studio in parallel through `scripts/ci/deploy-studio.mjs`: `nb-studio deploy`, waiting for the deployment, checking `/api/healthz` answers as `itam`, and checking the address serves the build's own `assets/index-*.js`. Each Studio is a GitHub environment, `studio-internal`, `studio-cn` and `studio-global`, holding the variables `NB_STUDIO_SERVER` and `STUDIO_APP_URL` and the secret `NB_STUDIO_API_KEY`, the repository's CI key that `nb-studio build ci setup nocobase/NocoITAM --reveal` makes on that Studio and pipes to `gh secret set --env`. A Studio that fails does not stop the others, and running the workflow by hand on a release tag deploys that release again. `package.json` names no `packageManager`, so the workflows pin pnpm themselves; keep it at the version the lockfile is written with.

`.github/workflows/ci.yml` runs the same checks on every push to `main` and every pull request, and builds a pull request too (2026-10-28); it pins the same pnpm and action versions as `deploy-studio.yml` and `release.yml`, so change them in all three.

cn and global are public: they run with `APP_SAMPLE_DATA=false`, in Chinese and English respectively, with no AI model configured, and with the configuration's default administrator (no `INITIAL_ADMIN_PASSWORD`), a decision of 2026-10-23. To deploy by hand instead, build the same archive and run `nb-studio --profile <profile> deploy --app itam --repository nocobase/NocoITAM --sha <commit> --file storage/exports/dist.tar.gz --json`, always naming the profile, since the CLI's current profile may be another Studio.

## The lockfile is pnpm 10's (2026-11-10)

CI, release and deploy install with pnpm 10.34.5 and `--frozen-lockfile`, and package.json names no `packageManager`. A newer local pnpm (12) writes the patched dependencies and peer suffixes in a form pnpm 10 rejects, and even its frozen install rewrites the file. After changing dependencies or `patches/`, write the lockfile with `npx pnpm@10.34.5 install --lockfile-only` and check it with `npx pnpm@10.34.5 install --frozen-lockfile --lockfile-only` before pushing.
